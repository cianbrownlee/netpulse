# Benchmarks

How fast NetPulse's capture pipeline is, what limited it, what changed, and one thing the
measurements proved wrong along the way. Every number comes from a command in this repo; each
change was measured on its own.

**Machine:** AMD Ryzen 9 9955HX (16 cores / 32 threads), Ubuntu 24.04 under WSL2, GCC 13.3,
libpcap 1.10.4, `RelWithDebInfo` build.

## TL;DR

Live capture of loopback traffic generated by iperf3 (10 s each; `tools/bench_live.sh`):

| | First version | Final |
|---|---|---|
| TCP bulk: NetPulse CPU | 47% of a core | **5%** |
| TCP bulk: iperf3 throughput *while being captured* | 18.9–19.6 Gbit/s | **78.5–79.8 Gbit/s** (no capture at all: 92–97) |
| TCP bulk: missed packets | 0.12% | **0** |
| UDP flood (64-byte packets, ~350k/s): NetPulse CPU | 19% of a core | **6%** |

The pipeline itself, under synthetic load (`netpulse_bench`, medians of 3 runs):

| | Baseline | A: no per-packet allocation | **B: + batched hand-off** |
|---|---|---|---|
| Max throughput | 2.73 M packets/s | 4.55 M | **8.33 M (3.0×)** |
| CPU per packet | 505 ns | 401 ns | **167 ns (−67%)** |
| Heap allocations per packet | 1.08 | 0 | 0 |
| Dropped at 3 M packets/s offered | 8.7% | 0.14% | 0.06% |

## The investigation

### 1. Something is expensive

The first live run showed NetPulse using **47% of a core to capture ~73k packets/s of TCP**,
about 6 µs per packet, when parsing and counting a packet should take well under 1 µs. A
per-thread breakdown during that run:

| Thread | User CPU | System CPU | Voluntary context switches |
|---|---|---|---|
| capture | 0.47 s | **3.50 s** | **148,780** |
| aggregator | 0.50 s | 0.83 s | 141,647 |

Almost all the time was in the kernel, with each thread sleeping and waking ~12,000 times a
second. The obvious suspects were in NetPulse's own hand-off between the threads: the queue's
lock taken once per packet, and a heap allocation per packet (a `std::vector` for its bytes plus
`std::deque` nodes), allocated on one thread and freed on the other.

### 2. Fixing the pipeline's own costs (A and B)

**A. No heap allocation on the hot path.** A queued packet became a fixed-size value (a 256-byte
inline array; NetPulse keeps at most 192 bytes of a packet, and the parser never needs more than
138) instead of a heap-allocated vector, and the queue became a ring of slots allocated once at
startup instead of a `std::deque`.

**B. Batched hand-off.** The capture side gathers packets into batches of up to 256 and queues a
whole batch under one lock; the aggregator takes up to 256 per lock. One lock acquisition and
one wake-up cover hundreds of packets instead of one. Batches are flushed every time libpcap
hands back a block, so this adds no latency beyond the kernel's own buffering. The batch size is
a setting, and `--batch 1` reproduces step A exactly, which is how A and B were measured apart.

Both were measured with `netpulse_bench`, which drives the real pipeline with synthetic packets
and no kernel in the loop (details below): together, 3× the throughput at a third of the CPU per
packet.

### 3. Live check: UDP improved, TCP didn't

| Live, 10 s | Before A+B | After A+B |
|---|---|---|
| UDP flood: NetPulse CPU | 19% | **6%** |
| TCP bulk: NetPulse CPU | 47% | **46%** |
| TCP bulk: capture-thread wake-ups | 148,780 | **149,622** |

The tiny-packet flood improved as predicted. TCP bulk didn't move at all, so the diagnosis in
step 1 was incomplete: something other than NetPulse's queue was waking the capture thread every
few packets.

### 4. The kernel was copying whole packets

libpcap hands packets over in 256 kB blocks from a ring buffer shared with the kernel. If the
kernel copied 192 bytes per packet, a block would hold ~1,000 packets. Wake-ups per packet, by
packet size (UDP, similar packet rates):

| Datagram size | Packets per capture wake-up |
|---|---|
| 100 bytes | 465 |
| 8,000 bytes | 16 |
| 60,000 bytes | **2.2** |

The ring was filling by packet *size*: the kernel was copying **entire packets** into it, and
libpcap applied the 192-byte snaplen only afterwards, in user space. (That's how libpcap's
memory-mapped capture path on Linux works.) Loopback TCP arrives as ~64 kB offloaded segments, so
every few packets filled a block and woke the capture thread.

This also meant the README's claim at the time, that packet payloads "are never captured at
all", was **false**. NetPulse's code never read past the headers, but full payloads were landing
in its memory.

**C. Truncate in the kernel.** A socket filter's return value is how many bytes of a packet the
kernel keeps, so NetPulse attaches a one-instruction BPF filter, "return 192", to the capture
socket. The kernel now truncates *before* copying:

| Datagram size | Packets per wake-up, before C | After C |
|---|---|---|
| 100 bytes | 465 | 439 |
| 8,000 bytes | 16 | 453 |
| 60,000 bytes | 2.2 | **348** |

| TCP bulk, 10 s | Before C | After C |
|---|---|---|
| NetPulse CPU | 46% of a core | **5%** |
| Capture-thread wake-ups | 149,622 | **6,273** |
| Packets seen | ~63k/s | ~244k/s (the traffic got faster; see below) |
| Missed | 0.09% | **0** |
| **iperf3 throughput** | **19.6 Gbit/s** | **78.9 Gbit/s** |

The last row was the surprise. The whole-packet copy happens in the *sender's* kernel path, so
NetPulse wasn't just expensive, it was **slowing down the traffic it was measuring**. A control
run, alternating no capture with capture, 3 rounds:

| Loopback TCP | Throughput |
|---|---|
| Nothing capturing | 92.3–96.8 Gbit/s |
| NetPulse capturing, with C | 78.5–79.8 Gbit/s (~16% lower: the inherent cost of tapping every packet) |
| NetPulse capturing, before C | 18.9–19.6 Gbit/s (~79% lower) |

(The "before C" figures come from two earlier runs on the same machine, not from the interleaved
control run, since that binary had been replaced by then.)

Truncating the copy doesn't change reported sizes, which come from each packet's on-the-wire
length: over a 5 s TCP run, NetPulse counted 100.21% of the bytes iperf3 sent, the extra being
headers, ACKs and iperf3's control connection.

## Synthetic benchmark: the pipeline itself

`netpulse_bench` pushes synthetic packets (2,000 conversations mixing HTTPS, SSH, DNS and
call-like UDP) through the real pipeline (queue, parser, aggregator, snapshots, classifier,
status checks), with no libpcap or kernel in the loop. It measures NetPulse's own cost
repeatably and needs no capture permission.

```bash
~/netpulse-build/netpulse_bench                     # max throughput: the producer waits for room
~/netpulse-build/netpulse_bench --rate 3000000      # fixed offered rate; the producer never waits,
                                                    # as live capture doesn't, so overload shows as drops
~/netpulse-build/netpulse_bench --batch 1           # step A behavior (no batching)
```

The baseline was measured by building this same harness against commit `591ce97` (the code before
A and B, with a two-line shim so the newer harness compiles; the shim configures batching, which
that code doesn't have).

### Maximum throughput (10 M packets; three runs each)

| Run | Baseline | A | B |
|---|---|---|---|
| 1 | 2.81 M/s, 496 ns CPU | 4.67 M/s, 388 ns | 8.36 M/s, 166 ns |
| 2 | 2.70 M/s, 514 ns | 4.50 M/s, 405 ns | 8.33 M/s, 167 ns |
| 3 | 2.73 M/s, 505 ns | 4.55 M/s, 401 ns | 8.19 M/s, 169 ns |

### Fixed offered rate (12 M packets; the producer never waits)

Drop rates are only comparable at equal offered load, so the *achieved* offered rate is reported
too. The baseline's producer couldn't exceed ~3.2 M packets/s at all: it was slowed by the same
per-packet allocation.

| Offered (target) | Baseline: offered → dropped | A | B |
|---|---|---|---|
| 2 M/s | 2.00 → 0.05% | 2.00 → 0.07% | 2.00 → 0.01% |
| 3 M/s | 2.96 → **8.72%** | 3.00 → 0.14% | 3.00 → **0.06%** |
| 4 M/s | 3.23 → 13.0% | 3.99 → 1.22% | 4.00 → 0.39% |
| 6 M/s | 2.99 → 7.59% | 5.02 → 29.5% | 5.98 → **0.94%** |

Small drop rates below capacity (e.g. 0.39% at 4 M/s for B) come from the harness pacing in
bursts of 4,096 packets into a 4,096-slot queue, not unlike real traffic bursts.

All runs account for every packet (`processed + dropped = sent`), and every mode also runs clean
under ThreadSanitizer.

## Live benchmark

```bash
tools/bench_live.sh ~/netpulse-build/netpulse 10
```

iperf3 generates traffic over the loopback interface while NetPulse captures it, which includes
everything the synthetic benchmark leaves out: libpcap, the kernel's capture ring, and the real
arrival pattern. Loopback TCP reaches the capture as ~64 kB offloaded segments rather than
1,500-byte packets, so ~80 Gbit/s is ~250k packets/s. The UDP flood (limited by iperf3 itself at
roughly 300–400k packets/s here) is the packet-rate stress test.

Final results:

| Test (10 s) | iperf3 | Packets/s seen | Missed | NetPulse CPU |
|---|---|---|---|---|
| TCP bulk | 78.9 Gbit/s | ~244k | 0 | 5% of a core |
| UDP flood, 64-byte packets | 188 Mbit/s | ~306k | 0 | 6% of a core |

## What's not done

The queue is still a plain mutex + condition variable. A lock-free queue would be the next step
only if a measurement pointed at the lock, and with batching it's taken a few thousand times a
second. These are loopback and synthetic numbers on one machine; capture on a physical NIC would
add driver and interrupt costs not measured here.
